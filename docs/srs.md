# 要求仕様書（SRS）

Simple Self Introduction

- 規格: ISO/IEC/IEEE 29148:2018 の構成に準拠する
- 根拠: [01-seed.md](./01-seed.md)
- 対象読者: 実装するコーディングエージェントおよびレビュア
- 優先順位（衝突時）: **情報を欠落させない > 読みやすさ（セクション区切り・余白） > 整列 > 装飾・動き**。A4 1 枚に収めることは求めない

本文中の ID（`SRS-F-*` など）はトレーサビリティ用である。実装は ID をコードに埋め込む必要はない。

---

## 1. 導入

### 1.1 目的

`contents/self-introduction.md` を唯一のコンテンツ源とし、ブラウザで閲覧でき、印刷（PDF 保存）すると縦長 A4 に出力される自己紹介ページを提供する。ページ数は 2 枚以上でもよい。

想定読者は、作者が所属する派遣会社の社員で、**別の案件にアサインされている同僚**である。採用選考や取引先への営業資料ではない。1 ページ目で「今どの案件で何をしている人か」が分かること。

### 1.2 範囲

本システムが提供するもの:

- Markdown の解析と HTML への変換
- 開発用 HTTP サーバ（`pnpm dev`、`http://localhost:3210`）
- 本番ビルド（`pnpm build`）で、開発サーバと同じ完成 HTML と CSS を `dist/` に出す
- Cloudflare Pages への静的ホスト（Git 連携または Wrangler）
- 画面表示用および印刷用のスタイル
- 上記を支える TypeScript のビルド・型検査・Lint

本システムが提供しないもの（非ゴール）は 1.4 を正とする。

### 1.3 文書の位置づけ

| 文書 | 役割 |
| --- | --- |
| [01-seed.md](./01-seed.md) | 意図の起点。本 SRS と衝突する場合は seed を優先し、SRS を直す |
| 本 SRS | 実装・検証の契約 |
| [design-system.md](./design-system.md) | 色・活字・余白・部品の再現仕様。見た目はここを正とし、変えたら CSS と同時に直す |
| `.agent/feature_list.json` | SRS から導出した、E2E で確認できる作業単位 |
| `contents/self-introduction.md` | 表示する本文。アプリコードより優先するコンテンツ |

### 1.4 非ゴール

次は作らない。提案もしない。

- CMS、管理画面、Markdown 編集 UI
- 認証、データベース、外部 API 連携
- 複数ページ、クライアントサイドルーティング
- React / Vue / Svelte / Next.js などの UI フレームワーク
- コンポーネントライブラリ、アイコンフォント、アニメーションライブラリ
- Tailwind CSS および CSS-in-JS
- GitHub Pages など、Cloudflare Pages 以外のホスティング設定
- CI での PDF 生成、自動スクリーンショット
- i18n、テーマ切替、ダークモード
- Markdown の拡張構文（GFM テーブル記法の入力、脚注、数式）の新規サポート

### 1.5 用語

| 用語 | 意味 |
| --- | --- |
| ソース Markdown | リポジトリルート相対で `contents/self-introduction.md` |
| ページ | 開発サーバまたは `dist/index.html` が返す単一 HTML |
| 印刷 | Chromium 系ブラウザの「印刷」→「PDF に保存」。用紙は A4 縦 |
| frontmatter | ソース Markdown 先頭の YAML（`---` で囲む） |
| AST | unified / remark が扱う Markdown 抽象構文木 |

## 2. 製品概要

### 2.1 利用の流れ

1. 開発者が `pnpm install` のあと `pnpm dev` を実行する
2. ブラウザで `http://localhost:3210/` を開く
3. ソース Markdown の内容が 1 枚のページとして表示される
4. ブラウザの印刷機能で PDF を保存すると、用紙は縦 A4。2 ページ以上になってよい
5. `pnpm build` で同じページが `dist/` に出る。Cloudflare Pages に載せて URL で配る

### 2.2 利用者

| 利用者 | 関心事 |
| --- | --- |
| 本人（コンテンツ編集者） | Markdown を直すだけでページが追従する |
| 閲覧者（同じ派遣会社の、別案件の同僚） | 今の担当とできることが斜め読みできる。PDF でも同じ情報 |
| 実装エージェント | 本 SRS と既存ツールチェーンだけを根拠に実装できる |

### 2.3 前提と依存

- Node.js は Vite 8 系が要求するバージョン（実装時の最新安定版に合わせる）
- パッケージマネージャは **pnpm のみ**（npm / yarn の lock を追加しない）
- ソース Markdown の文字コードは UTF-8
- 印刷確認の基準ブラウザは Chromium 系（Google Chrome または Microsoft Edge の現行安定版）
- 既存の `biome.json` / `lefthook.yml` / `.vscode` を壊さない

### 2.4 設計上の制約（技術スタック）

seed の希望を必須制約とする。

| 項目 | 制約 |
| --- | --- |
| 言語 | TypeScript。`strict: true`。`any` 禁止 |
| バンドル / dev server | Vite。ポート **3210** |
| Markdown | unified エコシステム（`unified` + `remark-parse` を中核とする） |
| スタイル | リポジトリ内のプレーン SCSS 1 系統のみ |
| Lint / Format | 既存 Biome |
| パッケージ | pnpm。依存は目的ごとに必要最小 |

許可する unified 周辺パッケージの例（同等の役割なら差し替え可）:

- `remark-parse`, `remark-rehype`, `rehype-stringify`
- `remark-frontmatter` および YAML の解析
- リンク化が必要なら `remark-gfm` の自動リンク相当、または同等の自前処理

禁止:

- Markdown を正規表現だけで HTML にする実装
- ページ本文を TypeScript にハードコードする実装

### 2.5 ディレクトリと責務

新規コードは次に置く。名前の微差はよいが、責務の混在は不可。

```text
src/
  markdown/     # ファイル読取、frontmatter、プレースホルダ、remark パイプライン
  render/       # AST または hast からページ HTML を組み立てる。I/O しない
  styles/       # 画面用・印刷用 CSS
  vite-plugin-self-intro.ts  # Vite から上記を呼び、開発時のルート HTML と dist を出す
index.html      # Vite の入口。中身はプレースホルダでよい
vite.config.ts
tsconfig.json
contents/self-introduction.md
```

- I/O（ファイル読み込み、Vite フック）は `markdown/` または Vite プラグインに閉じる
- Markdown → 構造化データ → HTML は純関数としてテスト可能な形にする
- `contents/` 以外の Markdown を探索しない

### 2.6 既存ファイル

変更してよい: `package.json`, `pnpm-lock.yaml`, `README.md`（起動方法の追記）

原則変更しない: `contents/self-introduction.md`, `biome.json`, `lefthook.yml`, `.vscode/*`, `LICENSE`

## 3. 外部インタフェース

### 3.1 入力: ソース Markdown

パス: `contents/self-introduction.md`

#### 3.1.1 frontmatter

YAML オブジェクト。既知キー:

| キー | 型 | 必須 | 用途 |
| --- | --- | --- | --- |
| `name` | string | はい | 氏名。見出しの `{name}` 置換にも使う |
| `summary` | string | いいえ | 氏名直下の 1〜2 行の導入。何ができる人かの輪郭 |
| `updated` | string | いいえ | 時点表示。`YYYY-MM` または `YYYY-MM-DD` なら「YYYY 年 M 月時点」 |
| `github` | string (URL) | いいえ | ヘッダのリンク。ラベル（GitHub）と URL を併記。href は URL |
| `blog` | string (URL) | いいえ | ヘッダのリンク。ラベル（Blog）と URL を併記。href は URL |
| `x` | string (URL) | いいえ | ヘッダのリンク。ラベル（X）と URL を併記。href は URL |

未知キーは無視する（落ちない）。必須キー欠落時は 3.3。

#### 3.1.2 本文の構造（現行ファイルに基づく契約）

実装は現行ファイルに特化してよいが、**同じパターンの増減**で壊れないこと。

| Markdown | ページ上の役割 |
| --- | --- |
| 見出し 1（`# {name}` など） | ページタイトル。`{name}` は frontmatter の `name` で置換 |
| 見出し 2 | 大セクション。現行は業務 → スキル → 資格 → 今後挑戦したいこと → 趣味 |
| 見出し 3 | 大セクション内の小見出し（趣味の項目など） |
| 見出し 4 | 見出し 3 の内側の分類。現行は趣味「生成 AI と戯れる」内の課金サービス。新しいセクションやグリッド単位にはしない |
| 段落 | 本文 |
| 箇条書き | 3.1.3 の規則でレイアウト |
| 単独行の URL | 外部リンクとして表示する |

本文中の `{name}` は見出し以外に現れても同様に置換する。

#### 3.1.3 箇条書きのレイアウト規則

資格・スキル・課金は密に並べる。その他のフラットなリストは、通常の縦並びにする。

| 文脈 | 表現 |
| --- | --- |
| 見出し 2「資格」直下のリスト | 表。可能なら「名称」と「取得」の 2 列（末尾の括弧を取得列にしてよい）。行はリスト項目と 1:1 |
| 見出し 2「スキル」直下の入れ子リスト | 親はカテゴリラベル（タグにしない）、子はタグ。同じ親の子は同じ行に並べ、探すときに行で辿れる |
| 見出し 4「課金中のサービス」直下のフラットなリスト | タグ（チップ）を横並び。折り返してよい |
| その他の入れ子リスト | 親を短い見出しまたは表の左列、子を右列。深くても **見える階層は 2 段まで** |
| その他のフラットなリスト | 通常の縦並び箇条書き |

リスト項目のテキストは省略・要約しない。

#### 3.1.4 リンク

- `http://` / `https://` で始まる URL は新しいタブで開く（`target="_blank"` と `rel="noopener noreferrer"`）
- frontmatter の github / blog / x はヘッダに横並びで出す。リンクはラベルと URL を併記し、`href` は URL。PDF でも URL が読めること。QR コードは置かない
- 本文の自動リンクは、表示テキストから `http://` / `https://` を省いてよい（href は絶対 URL のまま）

### 3.2 出力: HTTP

| 項目 | 要求 |
| --- | --- |
| URL | `http://localhost:3210/` および `http://127.0.0.1:3210/` |
| メソッド | GET |
| 成功 | `200`、`Content-Type: text/html; charset=utf-8` |
| 本文 | ソース Markdown を反映した完成 HTML（骨組みだけ返してブラウザで Markdown を再取得しない） |
| その他パス | Vite の開発アセットとして必要なもの以外は定義しない。アプリの第 2 ページは作らない |

`pnpm dev` は Vite の開発サーバを **3210** で起動する。他ポートへのフォールバックはしない（使用中なら失敗してよい。エラーは読み可能であること）。

開発中にソース Markdown を保存したら、ブラウザは自動で更新されること（Vite の HMR またはフルリロード）。

### 3.3 入力異常

| 状況 | 振る舞い |
| --- | --- |
| ファイルが無い | サーバは起動してよい。ページは HTTP 500 相当か、ページ内にエラーメッセージ。コンソールにパスを出す。空ページで成功扱いしない |
| YAML が壊れている | 同上。スタックトレースだけ出して無言で落ちない |
| `name` が無い | タイトルはファイル名や「Untitled」にせず、エラーとして表示する |
| 本文が空 | ヘッダ（name、任意のサマリ、URL リンク）だけ出してよい |

本番用の障害監視は不要。開発者が原因を特定できればよい。

## 4. 機能要求

### SRS-F-001 開発サーバ起動

`pnpm dev` で開発サーバが起動し、標準出力に `http://localhost:3210` が分かる表示がある。

### SRS-F-002 ページ表示

`http://localhost:3210/` を開くと、ソース Markdown の情報がすべてページ上に存在する（文言の欠落なし）。装飾のための言い換えはしない。

### SRS-F-003 Markdown 変換

変換は unified（remark）パイプラインで行う。見出し・段落・リスト・リンク・frontmatter を構造として扱う。

### SRS-F-004 ヘッダ

ページ先頭に氏名を置く。`summary` があれば氏名の直下に導入文として出す。存在する frontmatter の github / blog / x は、ラベルと URL を併記したリンクとして出す（横並び可）。氏名は見出し 1 と重複してよいが、視覚的に二度大きく出さない（見出し 1 をヘッダに統合してよい）。

### SRS-F-005 セクション構成

見出し 2 ごとにセクションを分ける。隣り合う見出し 2 セクションは、**余白を主**として一目で区別する。セクションを枠で囲まない（左右の縦線を置かない）。見出し 2 の直下に、見出し幅に収まる短い水平の罫線（見出しと同じアクセント色）を置いてセクションラベルとする。趣味の見出し 3 は、画面幅が足りれば **2 列**に並べてよい。

### SRS-F-006 コンテンツ追従

ソース Markdown に見出し 2 / 見出し 3 / 見出し 4 / リスト項目 / 段落を足したり削ったりしても、変換規則は同じで、特定の日本語見出し名へのハードコードに依存しすぎない。ただし 3.1.3 の例外（「資格」「スキル」「課金中のサービス」など）は見出しテキストで分岐してよい。

### SRS-F-007 印刷 A4 縦

Chromium の印刷プレビューで用紙 A4、縦、余白は CSS `@page` に従う。**ページ数が 2 以上でもよい。** 本文が切れない。1 枚に収めるためにフォントを 9pt 未満にしない。

## 5. 印刷要求

基準: Google Chrome の印刷ダイアログ。

| ID | 要求 |
| --- | --- |
| SRS-P-001 | `@page { size: A4 portrait; }` を指定する |
| SRS-P-002 | ページ余白は **10mm〜14mm**。本文が端に張り付かない |
| SRS-P-003 | 見出しの直後で改ページしない。短い塊（見出し 3 ブロック、見出し 4、スキル行、表の行、タグ列）は `break-inside: avoid`。長いセクション全体を無理に 1 ページへ閉じ込めない |
| SRS-P-004 | 印刷時のページ背景は白。画面の紙色は印刷しない。タグは印刷時に枠線＋白背景とし、分類は色ではなくラベルで示す |
| SRS-P-005 | 画面専用の dev 用 UI（あれば）は印刷しない |
| SRS-P-006 | フォントサイズの下限は印刷時 **9pt**。これ未満にしない |
| SRS-P-007 | 1 枚に収めるために余白やフォントを削らない。**文字を切る・9pt 未満に縮小する**ことは禁止。2 枚以上は合格 |

ブラウザが挿入するヘッダ/フッタ（日付・URL）は CSS では完全に消せない。検証時は印刷ダイアログで「ヘッダーとフッター」をオフにして確認する。この手順を README に 1 行書いてよい。

現行のソース Markdown 分量で 2 枚以上になってよい。情報の欠落より読みやすさを優先する。

## 6. デザイン要求

「洗練」は次の制約で定義する。抽象語だけの解釈はしない。**数値・部品の再現は [design-system.md](./design-system.md) を正とする。** 本節は要求の要約である。

### 6.1 トーン

編集的で静かな、同じ会社の同僚向けの自己紹介。余白の多い人物紹介に寄せる。採用用の職務経歴書、スタートアップのランディングページ、ダッシュボード、ガラスモーフィズム、大きなグラデーション、ヒーロー画像は禁止。ページ数は A4 2 枚以上でもよい。

### 6.2 レイアウト骨格

1. ヘッダ: 氏名、任意の時点（`updated`）、任意のサマリ（本文よりやや大きく、行間を広め）、その下に URL リンク（ラベル＋ URL、横並び）。リストにはアクセント色の小さいダイヤ形ビュレット。下に 1px 程度の罫線（ページの身元と本文を分ける、唯一の全幅ルール）
2. 本文: 最大幅は A4 から余白を引いた幅に近づける（画面でもおおよそその幅で中央寄せ）
3. 見出し 2 ごとのセクションは、隣との間の余白で区別する。四辺の枠・左アクセントの縦線は置かない。見出し 2 は字間・アクセント色と、見出し幅に収まる短い下罫線（見出しと同じアクセント色）でセクションラベルとして出す。サイズは本文の 1.15〜1.4 倍
4. 見出し 3 は本文の 1.1〜1.2 倍・太字。行頭に補助色の右向き三角を置き、大見出しの内訳であることが斜め読みで分かるようにする（CSS の形。文字の ▶ は絵文字になることがあるので使わない。横線・URL のダイヤ・セクションの縦線にもしない）。見出しの上余白は下余白より広く（およそ 3:1）、直後の本文の持ち物として見せる。趣味の見出し 3 ブロックはグリッド（自動で 1〜2 列）。ブロック同士は余白で分ける（ブロック間の罫線は置かない）
5. 見出し 4 は見出し 3 より小さく（本文の 1.0〜1.1 倍・太字。補助色でもよい）。見出し 3 ブロックの内側に置き、グリッドの列にはしない。見出し 3 ブロック間より狭い余白で、直後のリストのラベルとして見せる
6. 画面に独立フッターは置かない。本文末尾はソースの最後の見出し 2。印刷時のみ、氏名と時点の識別を各ページに出してよい（Chrome のページ番号カウンタや組版ツールは使わない）

### 6.3 トークン

実装は CSS カスタムプロパティに落とす。読みやすさのための余白・字間の微調整は許可する。系統は変えない。

| トークン | 指定 |
| --- | --- |
| 背景 | `#f6f4ef`（暖色の紙） |
| 本文色 | `#1c1b19` |
| 補助色 | `#5c5852` |
| 罫線 | `#d4d0c8` |
| アクセント | `#2c4a6e`（リンクと見出しのごく一部。全面には使わない） |
| タグ背景 | `#ece8e0`（課金タグなど。印刷時は使わず枠線＋白） |
| スキル親タグ背景 | 使わない。スキルの親はタグではなくラベル（補助色） |
| 本文フォント | 和文は `"Hiragino Mincho ProN", "Yu Mincho", "YuMincho", serif` を優先。欧文・URL は `"Iowan Old Style", "Palatino Linotype", Palatino, serif` でも、和文と同じでもよい |
| UI ラベル（リンク、タグ） | ゴシック（`"Hiragino Sans", "Hiragino Kaku Gothic ProN", sans-serif`） |
| ベースサイズ（画面） | 16px 相当。1 枚に収めるために下げない。印刷時は 9pt 以上 |
| 行間 | 本文 1.55〜1.7 |
| 見出し | 明朝のまま。見出し 2 は本文の 1.15〜1.4 倍。見出し 4 は本文と同程度〜1.1 倍。巨大タイトル禁止 |

### 6.4 禁止する見た目

- 絵文字、大きな丸アイコン、スキルのプログレスバー
- ドロップシャドウの多用、ぼかし、ホバーで大きく動く演出
- 原色のボタン、カードの立体感
- セクションごとの背景色の塗り分け（タグ以外）
- セクションを四辺の枠や左アクセントの縦線で囲むこと

### 6.5 動き

ホバーでリンクの下線または色が変わる程度まで。スクロールアニメーション、フェードインは禁止。

### 6.6 レスポンシブ

主成果物は A4。画面幅が A4 相当未満のときは 1 列に畳む。モバイル専用デザインは作らない。

## 7. 品質要求（ソフトウェア）

| ID | 要求 |
| --- | --- |
| SRS-Q-001 | `tsconfig` は `strict: true`。`noUncheckedIndexedAccess` を推奨 |
| SRS-Q-002 | `any`、`as` による逃げ、非 null 断言の常用は禁止。境界（YAML パーサ）のみ型ガードする |
| SRS-Q-003 | 公開関数・型の名前は英語。動詞 + 目的語 |
| SRS-Q-004 | コメントは「なぜ」だけ。自明な処理の説明は書かない |
| SRS-Q-005 | `pnpm exec biome check .` がエラーなし |
| SRS-Q-006 | `pnpm exec tsc --noEmit` がエラーなし |
| SRS-Q-007 | 例外を空 `catch` で握りつぶさない |
| SRS-Q-008 | 秘密情報・個人の連絡先（電話・メール）を新たに埋めない。ソース Markdown にあるものだけ出す |
| SRS-Q-009 | GitHub Actions が `pull_request` と default branch（`main`）への `push` で `pnpm check` を実行する。pnpm の lockfile を尊重する。Node バージョンは Vite の要求に固定する |

実装の着手順: **開発基盤（ローカルの `pnpm check`）→ CI → 開発サーバ → ページ機能**。品質ゲートをアプリより先に通す。

テスト:

- Markdown 変換（プレースホルダ、frontmatter、リスト構造）のユニットテストを **書いてよい**（必須ではない）
- E2E / Playwright は本バージョンでは必須ではない
- 検証の正は 9 章の手順

`package.json` スクリプト（名前は変更可、意味は固定）:

- `dev`: Vite、port 3210
- `build`: 型検査付きの本番ビルド。`dist/index.html` とページ CSS を出す。入力異常なら終了コードは非 0
- `check`: Biome check と `tsc --noEmit`
- `preview`: `dist/` を静的配信してローカル確認する
- `pages:deploy`: `pnpm build` のあと Wrangler で Cloudflare Pages に上げる

## 8. その他の要求

### 8.1 性能

ローカル開発で初回表示が数秒以内であればよい。特別な性能目標は置かない。

### 8.2 セキュリティ

信頼できるローカルファイルのみ読む。`eval` しない。生成 HTML はソース Markdown 由来のため、Markdown 中の生 HTML は **無効化**する（remark 既定のまま HTML を通さない）。XSS 対策としてユーザ入力フォームは存在しない前提。

### 8.3 アクセシビリティ（最小）

- ページは 1 つの `h1`（氏名）
- 見出しレベルを飛ばさない
- リンクテキストは URL 生文字でも、ラベルでもよいが、空のリンクは禁止
- 色だけに意味を持たせない（スキルの分類はラベル。印刷時のタグ色差に依存しない）

### 8.4 国際化

UI ラベル（タグ等）は英語または日本語で固定してよい。コンテンツ言語はソース Markdown に従う（日本語）。

### 8.5 ライセンス

既存 `LICENSE` を維持する。追加するフォントはシステムフォントのみ（ファイルを同梱しない）。

## 9. 検証

合格は実装者の自己申告ではなく、次を実行した結果で判断する。

### 9.1 コマンド

```bash
pnpm install
pnpm dev
```

別端末:

```bash
pnpm check
pnpm build
```

`check` 未整備の間は `pnpm exec biome check .` と `pnpm exec tsc --noEmit` で代替する。`pnpm build` のあと `dist/index.html` がソース Markdown の氏名と本文を含み、`dist/page.css` と `dist/list-layout.css` があること。

### 9.2 画面

`http://localhost:3210/` で確認する。

- 氏名が frontmatter の `name` と一致する
- github / blog / x の URL がヘッダに見え、ラベルと URL が併記され href と一致する
- 趣味（サイクリング、生成 AI）、業務、スキル、資格の文言がソースと対応する
- 課金サービスの名前がすべて見える。見出し 4「課金中のサービス」が「生成 AI と戯れる」の内側にある
- `github.com/gnkm/dotfiles` がリンクになっている
- スキルがカテゴリラベル付きの行で、1 列の長い黒丸リストだけで終わっていない
- 資格が読み取れる（表または同等の密度）
- 見出し 2 ごとのセクションが余白と、見出し直下の短い水平罫線で区別できる。セクション左右に縦線が無い
- 大見出しと小見出しのサイズ差が斜め読みできる
- 画面に独立フッターが無い

### 9.3 印刷

Chrome で印刷プレビュー:

- 用紙 A4、縦
- ヘッダーとフッター off
- 背景グラフィックはオフでよい（印刷背景は白）
- ページ数は 1 枚でなくてよい（2 枚以上可。3 枚を超えないよう余白は削りすぎない）
- 本文が切れていない
- フォントが 9pt 相当以上で読める
- 見出し 2 セクションの境界が印刷面でも分かる
- 見出しだけがページ末に残っていないこと（目視）

### 9.4 追従の煙テスト

ソース Markdown の段落を 1 行だけ足して保存し、リロードなし、または自動リロード後にその行が見えること。確認後は元に戻してよい。

### 9.5 完了条件（Definition of Done）

次をすべて満たす。

1. SRS-F-001〜007 を満たす
2. 9.1〜9.3 が通る
3. 非ゴールのものを実装していない
4. 既存の Biome / lefthook / ソース Markdown が意図せず壊れていない
